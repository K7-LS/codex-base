# Проверка профессиональной основы

`cases.json` содержит 15 синтетических ситуаций из согласованного проекта
основы от 7 сентября 2026 года. Это проверяемые требования к поведению.
Статус `DESIGN_ONLY_NOT_RUN` означает, что файл не подтверждает результат
модельного прогона. Случаи перенесены без изменения из проектного анализа.

Сценарии проверяют обычную ВОР, различение поставки и монтажа, уместность
вопросов, обоснованное возражение, независимость источников, изменение задачи,
недоступный инструмент, инициативу, исправление ошибки, язык, границу ИД,
приоритет нового решения, актуальность рецензии и пересмотр вывода.

## Подготовка без модельных вызовов

```powershell
python tools/prepare_core_eval.py --output .work/core-eval/candidate-plan.json
```

Команда записывает хеши `AGENTS.md` и файлов в `agents`, `skills`,
`control-skills`, `cold`, `runtime`, хеш сценариев и пустой список прогонов.
Это ограниченный инвентарь методик и runtime, а не снимок всего checkout;
например, корневые `tools`, `schemas` и `catalog` в него не входят.
Она не устанавливает базу, не меняет профиль, не вызывает модель
и не подтверждает загрузку инструкций. Существующий файл не перезаписывается.
Для исходной базы нужен отдельный инвентарь из её неизменённого checkout.
Этот инвентарь шире старого matched A/B: он включает тела references,
скриптов и cold-методик, поскольку они могут менять результат после загрузки.

## Порядок содержательной приёмки

1. До прогона согласовать модель, клиент, инструменты, разрешения, число
   повторов и предел расхода. Предложение в `execution_protocol` ещё не
   разрешение. Модель и reasoning записываются в протоколе конкретного
   опыта, в инструкциях базы они не закрепляются.
2. Материализовать фикстуры в отдельной тестовой папке. Передать модели
   исходники и задачу; поля `must_observe` и `critical_fail` оставить
   проверяющему. Не выдавать ожидаемый вывод за содержание первоисточника.
   Краткие описания окружения в cases сами по себе не создают доступный tool.
3. Сравнивать исходную базу и кандидат при одинаковых условиях. Зафиксировать
   реальную версию клиента, effective model/config, overrides, инструменты
   и подтверждение загрузки нужных инструкций. Для C05 развилка открывается
   после чтения документов. Для C07 уточнение подаётся во время работы;
   единый стартовый prompt такой прогон не заменяет.
4. Сохранить локально фактический диалог, tool calls, выданные файлы и хеши
   окончательных байтов. Записать открытые вопросы, время до принятого
   результата, вмешательства пользователя и доступный фактический расход.
   Не переносить в публичный репозиторий credentials и реальные рабочие данные.
5. Независимый проверяющий оценивает каждый пункт по конкретному месту в
   диалоге или результате. Проставляет `PASS`, `FAIL` или `NOT_OBSERVED`,
   объясняет оценку и отмечает все критичные ошибки. Непоказанное действие
   остаётся `NOT_OBSERVED`; пустой протокол не становится успешным.
6. Любая критичная ошибка исключает приёмку этого прогона. После исправления
   повторить затронутые случаи; рецензия связывается с новыми байтами.
   Общий вывод отдельно указывает покрытые случаи, повторы и ограничения.

Совпадение нужных слов в `AGENTS.md`, проверка JSON, успешная сборка ZIP
и экономия контекста не доказывают профессиональное поведение. Мысленный
разбор сценария проверяющим полезен для ревью инструкций, но не заменяет
наблюдение модели в реальном клиенте. Release pipeline сам не запускает
модельные опыты. Для продвижения кандидата он теперь требует проверяемый
протокол содержательной приёмки.

## Контракт выпуска v1

`contract.json` задаёт отдельный контракт `k7-professional-core-v1`.
В нём сохранён SHA-256 исходного `cases.json`, а каждому исходному условию
присвоен стабильный идентификатор: `C01.M01` для первого `must_observe`,
`C01.F01` для первого `critical_fail`. Хеш текста каждого условия проверяется.
Изменение исходных условий требует нового протокола; редактирование условий
под полученные ответы запрещено смыслом этой проверки.

Один принятый прогон каждого из 15 случаев даёт **покрытие требований**.
Это не оценка надёжности и не выполнение предложенных трёх повторов.
В evidence записывается `SINGLE_RUN_CONFORMANCE_NOT_RELIABILITY`.
Если приложено несколько прогонов, каждый должен пройти все свои условия;
нельзя спрятать неудачную попытку в среднем результате. Полнота представления
всех реально запущенных попыток остаётся обязанностью владельца эксперимента.

Кандидатский ZIP разрешено собрать до опытов: `CORE_BEHAVIOR` в offline
evidence остаётся `NOT_RUN`. Для финальной композиции, продвижения в stable
и создания `package-acceptance.json` один общий validator повторно проверяет:

- контракт во внешнем manifest и внутри неизменённого ZIP;
- SHA-256 и размер именно этого ZIP, хеш package manifest;
- наличие всех 15 случаев, всех исходных критериев и независимой рецензии;
- `PASS` для каждого наблюдаемого требования и `ABSENT` для каждого
  критичного дефекта; `FAIL`, `NOT_OBSERVED` и `NOT_EXERCISED` закрывают выпуск;
- существование и хеши локальных источников, фикстур, harness, evaluator,
  effective config, диалогов и рецензий;
- совпадение загруженных файлов базы с файлами проверяемого ZIP;
- существование каждого указанного JSONL-события и соответствие его хеша.

Удаление нового поля из manifest, самостоятельная запись верхнего `PASS`,
пересчёт собственного хеша или `--legacy-sync-bootstrap` не отменяют gate.
Последний флаг касается только прежнего контракта проверки публикации.
Текущий протокол `professional-core-v1` требует offline, core и canary.
Он записывает `MATCHED_AB: NOT_REQUIRED` с явной причиной. Исторический
matched A/B сохраняет свои исходные модель, режим и методику в отдельном
read-only validator; его два стартовых запроса не считаются проверкой новой
профессиональной базы и не создают дополнительного разрешения на вызовы.
Протокол canary сверяет фактический клиент и discovery с проверяемым пакетом.
Если пакет требует прежний клиент, опыт на новом клиенте не закрывает это
условие. Версию installer contract эта правка не меняет.

## Формат локального evidence bundle

Корневой JSON имеет `schema_version: 1`, `kind: core_behavior_evidence`,
`evaluation_mode: RELEASE_PACKAGE`, `protocol` из `contract_reference()`,
полную `release_binding`, `CORE_BEHAVIOR: PASS`, `claim` из контракта,
`evidence_body_sha256`, `artifacts` и `runs`.
В итоговом составном evidence этот объект хранится в `core_behavior_evidence`,
а верхний verdict — в `CORE_BEHAVIOR`. Имя `core_behavior` для вложенного
объекта недопустимо: оно сталкивается с verdict в регистронезависимом
объекте PowerShell. Настоящий результат composition проверяется через
`ConvertFrom-Json` в PowerShell 5.1 и 7.
Список точных полей и их проверки находится в
`src/codex_base/core_acceptance.py`; пример синтетической структуры для
модульных тестов — `tests/core_evidence_support.py`. Этот пример никогда
не служит фактической рецензией или свидетельством прогона модели.

`artifacts` сопоставляет ID с `{path, sha256, bytes}`. Пути относительны
корневому JSON и находятся только в `core-artifacts/`, без выхода из папки,
symlink или junction. Они не могут подменять файлы release. Каждый файл
ограничен 32 MiB, весь набор — 256 MiB. Поля `suite_artifact`,
`harness_artifact` и `evaluator_artifact` ссылаются на соответствующие ID.
Пустой или изменённый файл не принимается. В публичный выпуск нельзя
включать реальные рабочие данные, credentials и полный секретный config.
Артефакт effective config содержит только нужные для опыта несекретные
настройки; модель, клиент и reasoning — фактические наблюдения без allowlist.

Каждый `run` содержит:

- уникальный `id`, исходный `case_id`, `status: PASS`, `subject_id`;
- `runtime`: `{client: {id, version}, model, reasoning_effort,
  effective_config_artifact}`;
- `events_artifact`, `fixture_artifacts`, `materialized_source_inventory`
  для всей доступной поверхности пакета и `loaded_source_inventory`
  для реально загруженного подмножества, обязательно включая `AGENTS.md`;
- `input_event`: ссылка на фактически отправленную исходную задачу с
  исходным `case_id`, точным текстом `prompt`, `case_spec_sha256`
  и хешами переданных фикстур;
- `source_load_event`: указатель на JSONL-строку с `kind: loaded_source`,
  `run_id`, `runtime`, `source_inventory_sha256`,
  `loaded_source_inventory_sha256`, `harness_sha256`
  и `fixture_hashes`;
- словари `must_observe` и `critical_fail` с исходными ID условий;
- `review`: `{reviewer_id, independent: true, artifact}`.

Условия содержат `{status, reason, evidence}`. `evidence` — непустой список
указателей `{artifact, line, sha256}`; `line` начинается с 1, хеш относится
к байтам конкретной JSONL-строки без перевода строки. Записанные поведенческие
события содержат `run_id` своего прогона. Служебная запись о загрузке базы
не считается свидетельством поведения. Каждому условию нужно хотя бы одно
событие модели или инструмента после отправки задачи. Одного пользовательского
вопроса недостаточно. Допускаются сообщения `assistant_message`/`user_message`
с непустым `text`, `tool_call`/`tool_result` с именем и аргументами/результатом
в `payload`, либо нативный `client_event` для `item/completed` с содержательным
`agentMessage`. Метаданные запуска задачи не подходят. Harness сохраняет нативное событие
внутри записи, не выдавая придуманную реплику за событие клиента.

Файл рецензии содержит `run_id`, `reviewer_id`, `independent: true`,
`case_id`, `input_event_sha256`, `verdict: PASS`, полный `criterion_statuses`, `events_sha256`,
`source_inventory_sha256`, `loaded_source_inventory_sha256`
и `evaluator_sha256`.
Рецензент отличается от исполняющего агента. Источник каждой оценки
проверяется по указанной строке диалога и окончательному результату.
Успешные исходные критерии необходимы, но не отменяют дополнительный
существенный дефект ядра, найденный рецензентом. Например, корректный текст
письма при скрытой незавершённой обязательной проверке не получает общий
PASS. Такой дефект фиксируют отдельно, сохраняя исходные критерии без
переписывания; общий verdict остаётся NOT PASSED до исправления и проверки.
Для C07 обязательны точное `mid_task_input_event`, а также фактические
`pre_mid_task_observation` и `post_mid_task_observation` с правильным порядком.
Содержательная сохранность таблицы оценивается рецензентом отдельно.

Локальная проверка уже существующих файлов:

```powershell
python tools/validate_core_behavior.py --evidence core-behavior.json --release-manifest release-manifest.json --package codex-base-VERSION.zip
```

При композиции дополнительно обязательны `--core-behavior-evidence` и
`--candidate-package`. Композиция и promotion сохраняют относительные
артефакты рядом с новым evidence, не меняя их байты. Проверка package
acceptance повторно читает эти файлы и ZIP.

`prepare_core_eval.py` по-прежнему выдаёт только `PREPARED_NOT_RUN`.
Пилот из `SOURCE_SNAPSHOT` нельзя автоматически повысить до приёмки ZIP,
даже при совпадении нескольких отдельных инструкций.
При сборке suite и contract берутся только из экспортированного Git commit.
Исторический commit без контракта остаётся историческим кандидатом и
текущий promotion его отклонит. Наличие нового файла в рабочей папке
не меняет байты пакета из прежнего commit.

Этот локальный gate подтверждает целостность, полноту заявленных наблюдений
и привязку к пакету. Хеш не доказывает подлинность исполнения или честность
рецензента. Подписанная аттестация исполнения здесь не реализована; проверка
поведения и разрешение на публикацию остаются отдельными основаниями.
При ошибке записи promotion может оставить неполную выходную папку без
stable manifest; для повторного запуска нужна новая пустая папка. Целиком
атомарное переименование набора файлов пока не реализовано. Успешный возврат
требует повторной проверки скопированного bundle.

## Доставка и ранее установленные consumers

Новая `sync-policy.json` требует `CORE_BEHAVIOR`, точный
`professional-core-v1` и reference контракта. PowerShell updater проверяет
это в подписанных evidence/manifest и сверяет контракт внутри ZIP.
Он не выполняет модельные опыты и не получает историю пользователя.
Модельные артефакты проверяет hub перед продвижением. Consumer доверяет
подписанному вердикту и не выполняет полный Python validator поведения.
Подпись и собственный хеш подтверждают происхождение и целостность файла,
но сами по себе не доказывают, что producer выполнил содержательный аудит.

Прежняя установленная policy требует `MATCHED_AB: PASS`. Она отклоняет новый
выпуск с честным `MATCHED_AB: NOT_REQUIRED` до установки вложенной новой
policy. Поэтому эта смена протокола не доставляется бесшовно через старый
updater. Нужен отдельный разрешённый и проверенный путь обновления
updater/installer либо подписанный переходный пакет. Такой переход здесь
не разработан, не опубликован и не проверен на рабочем consumer.
Нельзя обходить его выдуманным результатом старого A/B, отключением проверки
подписи или заменой локальной policy без разрешения.
Нельзя использовать и переход с заменой только policy: прежний script
перебирает `required_verdicts`, но не проверяет новые `required_protocol`
и `required_contract`. Такой гибрид ослабляет проверку; это вывод по коду,
а не результат запуска гибрида. Отдельно разрешённый доверенный installer
или переходный пакет должен доставлять новый script и policy вместе как
согласованный проверенный набор.

Правка доставки сделана после создания отдельного неизменяемого snapshot
поведенческого пилота. Результаты snapshot относятся к своим байтам и сами
по себе не принимают эту доставочную дельту или будущий ZIP.
