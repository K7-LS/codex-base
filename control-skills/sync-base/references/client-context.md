# Диагностика клиента и Dynamic context

`client-context.py` — отдельный локальный инструмент для Python 3.11 или новее.
Он показывает ограниченный набор настроек Codex и по явному решению пользователя
на Windows меняет только `features.context_management.experimental_mode`.
На других ОС доступны `inspect` и `plan`; запись и откат дают
`MUTATION_REQUIRES_WINDOWS_REPLACEFILE` до создания файлов. Обновление базы
не запускает этот инструмент автоматически. Модель, reasoning, окно контекста,
автокомпактизация и memories остаются выбором пользователя.

## Что считается проверенным

1. `toml: VALID` означает, что файл разобран `tomllib`. Это не проверка схемы Codex.
2. Явный `inspect --cli` запускает у выбранного бинарника только `features list`
   с двумя синтетическими конфигами: флаг выключен и включён. `RECOGNIZED`
   выдаётся, если обе записи реестра `context_management` соответствуют своим
   значениям и оба процесса завершились с кодом 0. Сам по себе код 0 ничего
   не доказывает: неизвестные ключи могут молча игнорироваться.
3. Проверка CLI не устанавливает, что Desktop использует тот же бинарник,
   загрузил этот файл или предоставил функцию текущему аккаунту. Значения
   `function_behavior`, `operation_tool_availability`,
   `account_experiment_availability`, `active_desktop_configuration` остаются
   `NOT_VERIFIED`. Наличие инструмента вопросов, computer use или другой
   возможности нужно проверять в конкретной задаче средствами host.

В официальной схеме ключ `features.context_management` допускает булево значение
или таблицу; поле таблицы `experimental_mode` имеет тип boolean. Этот редактор
намеренно поддерживает только обычную таблицу и отсутствие ключа. Схема и
документация: [справочник конфигурации](https://learn.chatgpt.com/docs/config-file/config-reference),
[JSON Schema](https://learn.chatgpt.com/docs/config-schema.json).
На проверенном CLI 0.153.1 флаг выводится как `under development`.
Это свидетельство конкретного бинарника на 10.09.2026, а не обещание будущей
поддержки. `--strict-config features list` у него не поддерживается.

## Порядок работы

Ни путь Python, ни путь пользовательского файла не подставляются автоматически.
Укажите уже доступный Python 3.11+, этот скрипт и точный `config.toml`.
Следующий пример использует переменные PowerShell с явными путями:

```powershell
$python = 'C:\path\to\python.exe'
$tool = 'C:\path\to\sync-base\client-context.py'
$config = 'C:\path\to\chosen\config.toml'
$cli = 'C:\path\to\verified\codex.exe'

& $python -B $tool inspect --config $config
& $python -B $tool inspect --config $config --cli $cli
& $python -B $tool plan --config $config --enable
```

`inspect` выводит только SHA-256 и разрешённые значения: модель, reasoning effort,
`features.memories`, форму/флаг context management, размер окна контекста и порог
автокомпактизации. Остальные значения, адреса MCP и переменные окружения не
выводятся. Неверный тип разрешённого поля обозначается без вывода его содержимого.
Не направляйте полный пользовательский конфиг агенту для выполнения этой проверки.

При `--cli` бинарник должен быть доверенным: инструмент исполняет указанный файл.
Ссылка/junction выбранного CLI сначала разрешается в полный путь конкретного
файла; оба запуска и SHA относятся к этому пути. Запрет ссылок при работе
с пользовательским конфигом остаётся в силе.
Для каждого запуска создаются отдельные пустые HOME, CODEX_HOME, APPDATA, TEMP
и XDG-каталоги. Пользовательский конфиг не копируется; персональный PATH,
токены и proxy-переменные не наследуются. Вывод и ошибки процесса не передаются
в отчёт: сохраняется только распознанная строка флага, код завершения и SHA
бинарника. Это изоляция конфигурации, не песочница ОС или запрет сетевого трафика.
Машинные политики клиента могут действовать независимо от временного home.
Команда не запускает модель, MCP или клиентский сеанс и ничего не устанавливает.

Перед записью просмотрите план и закройте редактор настроек, чтобы другой процесс
не сохранял этот файл одновременно. Возьмите `expected_sha256` из плана:

```powershell
& $python -B $tool apply --config $config --enable --expected-sha256 '<SHA-256 из плана>'
```

Для выключения замените `--enable` на `--disable` в плане и применении. Если флаг
отсутствует, выключение ничего не записывает. Повторное применение того же
значения возвращает `UNCHANGED` и не создаёт новую резервную копию.

Успешная запись возвращает `APPLIED`, новый SHA и `backup_receipt`.
`NEW_TASK_REQUIRED` означает: откройте новую задачу с нужным клиентом;
текущая задача не доказывает загрузку новой настройки. Это не автоматическая
проверка поведения и не требование перезапускать или закрывать работающую
задачу прямо сейчас. После перехода отдельно проверьте фактическую доступность
функции. Не называйте её работающей только по JSON-квитанции.

## Сохранность файла и откат

Файл должен существовать, быть обычным файлом с одной жёсткой ссылкой и не иметь
символических ссылок/reparse points в своём пути. Для записи требуется доступ
на запись. Файл только для чтения, нестандартная форма нужного TOML-фрагмента,
конфликт ключей или изменение SHA дают `REVIEW_REQUIRED`, код выхода 2.
Текст исключений и значения конфигурации не включаются в ошибку.

Редактор использует `tomllib` для разбора и проверки результата, а лексические
диапазоны — для изменения одного значения. Комментарии, остальной текст,
UTF-8 BOM и CRLF сохраняются; при добавлении таблицы используется существующий
тип перевода строк. Все прочие структуры сравниваются после TOML-разбора,
включая массивы, даты и `nan`. Поддерживаются:

```toml
[features.context_management]
experimental_mode = true
```

При отсутствии таблицы она добавляется в конец. Inline-таблицы родителя,
булева форма `context_management`, dotted/quoted-ключи или заголовки нужного
фрагмента и его вложенные таблицы требуют ручного решения. Инструмент не
пересериализует весь файл и не нормализует такую запись без согласования.
Сложные значения в посторонних разделах допустимы, если они валидны по TOML.

Перед записью рядом с конфигом создаются уникальные `.bak` и `.json` с маркером
операции. **Резервная копия содержит полный исходный конфиг, в том числе возможные
секреты.** Её содержимое не выводится. На Windows DACL исходника копируется в
пустой новый файл до записи данных.
Эти файлы не предназначены для публикации, прикладывания к отчёту или загрузки
агенту. Удаление копий не выполняется автоматически.

SHA проверяется перед подготовкой и непосредственно перед заменой, затем
перечитывается итог. Для записи, отката и аварийного восстановления используется
Windows `ReplaceFileW` с уникальным backup **фактически вытесненного файла**.
Его SHA сравнивается с ожидаемым. Если внешний редактор записал файл после
последней проверки, его байты сохраняются в `displaced_config`, а операция
возвращает `CONCURRENT_REPLACE_CONFLICT`, код 2, `config_replaced: true` и пути/SHA
файлов для восстановления. **Конфиг к этому моменту уже заменён; это конфликт
с сохранённой чужой редакцией, а не отказ без записи.** Автоматическая повторная
перезапись при таком конфликте не выполняется; требуется совместное решение,
какую редакцию восстановить. Даже совпавший displaced backup сохраняется:
чужой процесс может ещё дописать его через ранее открытый handle.

При любом отказе `ReplaceFileW`, включая частичное выполнение, оставшиеся
target/temp/displaced файлы сохраняются, их состояние перечитывается. Выдаётся
`REPLACE_FAILED_RECOVERY_REQUIRED`, числовой WinError и пути/SHA без содержимого.
Нельзя считать, что отказ API означает отсутствие изменений. Особые состояния
кодов 1175–1177 описаны в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
Ошибки переноса ACL не игнорируются.
При замене Windows может нормализовать `SE_DACL_AUTO_INHERITED` и происхождение
ACE (`INHERITED_ACE`) у незащищённого DACL. Это не побайтовая сохранность
дескриптора. Native-тест сверяет owner/group, порядок/тип/число ACE, SID, маски,
остальные флаги и `DACL_PROTECTED`; он подтверждает текущие права доступа
на проверенных файлах. Поведение при будущих изменениях ACL родителя отдельно
не проверялось.

Свой lock-файл исключает параллельные операции этого инструмента; внешний
редактор этот lock не соблюдает. При ошибке итоговой проверки исходник
восстанавливается только если текущие байты ещё равны собственному варианту;
само восстановление защищено тем же ReplaceFileW с захватом вытесненных байтов.
При аварийном завершении может остаться lock-файл;
он требует проверки владельца/работающего процесса и ручного решения, не
автоматического удаления.

Для отката укажите **квитанцию своей операции**, которую вернул `apply`:

```powershell
& $python -B $tool rollback --config $config --receipt '<полный путь backup_receipt>'
```

Проверяются имя/маркер операции, завершённый статус `APPLIED`, расположение рядом с тем же конфигом, SHA
резервной копии и возможность точно воспроизвести установленный вариант этим
же одношаговым изменением. Откат разрешён только при совпадении текущего SHA
с установленным вариантом. Незавершённые `PREPARED`/`ROLLBACK_PREPARED` и
конфликтные операции автоматически не откатываются. Если исходные байты уже восстановлены, результат —
`ALREADY_RESTORED`. Подделка квитанции не даёт право записать произвольный другой
конфиг: его повторно построенный результат обязан совпасть с текущими байтами.
Квитанция не является цифровой подписью и не защищает от злоумышленника с правом
изменять сам инструмент и пользовательские файлы.

## Проверка изменения базы

`tests/test_client_context.py` использует только синтетические файлы. Проверяются
сохранность TOML/байтов/прав, поддерживаемые и отклоняемые формы, отсутствие
утечек, drift, безопасное восстановление, откат, readonly, ссылки и распознавание
CLI с инертным process stub. Проверка настоящего CLI оформляется отдельно с
SHA бинарника и пустым home; она не заменяет проверку Desktop, аккаунта или
длинной рабочей задачи. Настройки модели, reasoning и лимитов в runtime базы
этим инструментом не задаются.
